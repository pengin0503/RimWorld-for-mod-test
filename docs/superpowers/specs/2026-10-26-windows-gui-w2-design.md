# Windows 版 W2：GUI の設計（ゲームの描画で作る）

日付：2026-10-26。状態：**実装済み（PR #11）・Windows 実機は未確認**。ユーザー承認 2026-10-26 10:40。前提は [Windows 版の設計](2026-10-26-windows-host-design.md) の W1（実装済み・PR #10 でマージ）。方式は 3 案からユーザーが「ゲームの描画で作る」を選んだ（2026-10-26 10:29）。描画だけを起動できることは [試作](../../research/2026-10-26-w2-render-spike.md) で確かめた。

## 目的

ユーザーが自分の Windows PC で、本家の部品で描いた画面から次の 3 つを行えるようにする。

1. 検証する MOD と構成（公式 DLC・依存 MOD・読み込み順・対象 MOD）を選ぶ。
2. 検証内容（A/B、マップ、C の材料候補）を指定して、W1 の検証を実行する。
3. 結果（合否・理由・新しいエラー・マップ・C の結果・確認していない範囲）を見る。

既存の事前検査 GUI（`tools/preflight_gui.py`、tkinter）を置き換える。

## 守ること

- **遊べる状態にしない。** メインメニュー（`Root_Entry`・`UIRoot_Entry`）を作らない。`Game` を作らない（できたら即終了）。シーンの切り替え要求があれば終了。開発モードは切る（開発者用の道具を出さない）。Steam を初期化しない。
- **判定しない。** 検証は今の `validation_host.py run` を子プロセスで呼び、画面は `result.json` を表示するだけ。AI が Linux で見る結果と同じファイルを見る。Windows の結果は `experimental` のまま表示する。
- **利用者の設定を変えない。** 画面のプロセスは、実行ディレクトリの中の私有の設定・ログを使う。本家の `ModsConfig.xml` は読み込み順の取り込みのために読むだけ。
- **ゲームの物を公開しない。** ゲームの DLL・素材・画面写真は公開リポジトリに入れない。

## 構成

```
validation_host.py gui ──起動──▶ RimWorldValidationGui（ゲームの描画、遊べない）
        │                              │ 検証を始める
        │                              ▼
        └──────────────────── validation_host.py run ──▶ Worker（描画なし。W1 のまま）
                                       │
                                       ▼
                              結果フォルダ（result.json・map.png など）──▶ 画面で表示
```

### 画面のプログラム（C#）

- 新しいプロジェクト `gui/RimWorldValidation.Gui`。ゲームの型（`Verse.Window`・`Verse.Root`・`Verse.UIRoot`）を継承するので、**ゲームの DLL を参照してビルドする**。参照先はビルド時に `-p:GameDir=<スナップショットの game フォルダ>` で渡す。ゲームの DLL は出力に含めない。
- 起動は試作と同じ手順（公式の `Bootstrap.Initialize` に沿って描画・入力・テクスチャを初期化し、メインメニューの代わりに自前の Root と UIRoot を置く）。非公開の手順はリフレクションで呼び、見つからなければ起動前に `adapterMismatch` で止める。
- 読み込むのは公式コンテンツだけ（画面の部品・翻訳・Def の名前のため）。検証する MOD は画面のプロセスでは読み込まない。
- 試作と同じく、Linux でも動く（クラウドでの画面確認用）。製品としての対象は Windows。

### 画面と Controller の役割分担

- 画面に依存しない処理（要求の組み立て、`result.json` の読み取り、理由コードの日本語の説明）は、ゲームを参照しない C# のライブラリ `gui/RimWorldValidation.Gui.Model` に置く。これは公開 CI でビルドとテストができる。
- `validation_host.py gui --snapshot <S> --results <DIR> [--mods <フォルダ> ...] [--mods-config <ModsConfig.xml>]`：
  - 画面用の実行ディレクトリを作る（W1 と同じリンク方式。私有の `userdata`）。
  - MOD の候補を `host/Mods` にリンクする。ゲームの `Mods`、Workshop のフォルダ（スナップショットの元のパスから `steamapps/workshop/content/294100` を探す）、`--mods` の追加フォルダ。リンクと元のパスの対応表も渡す（検証の要求には元のパスを書くため）。
  - 画面のプロセスを、W1 と同じ監視（Windows は Job Object、Linux はプロセスグループ）の下で起動し、閉じたら実行ディレクトリを消す。メモリ上限は描画の分だけ大きくする（値は実装時に計測して決める）。
- 画面から検証を始めると、`--results` の下に新しいフォルダを作り、要求 JSON を書いて `validation_host.py run` を起動する。進捗は子プロセスの出力の行で示す。中止は子プロセスを止める（W1 の監視がジョブごと止める）。

### 画面

本家の窓・タブ・一覧・ボタンで、次の 4 つのタブを持つ 1 つの窓にする。起動中は本家の読み込み画面がそのまま出る。

1. **MOD**（本家の MOD 管理画面に似せる）：左に使わない MOD、右に使う MOD（読み込み順。ドラッグで並べ替え）。公式 DLC の選択、対象 MOD の印、`Preview.png` と説明、足りない依存 MOD の警告。本家の現在の読み込み順を取り込むボタン。一覧はゲームの `ModLister` が作る。
2. **検証内容**：A/B の選択と言語。マップ（種、バイオームは本家の名前で選ぶ）。C の材料候補（レシピ・材料を本家の Def 名で選ぶか、MOD の Def 名を入力）。Harmony の期待値など細かい指定は、要求 JSON を貼り付ける欄で行う。
3. **結果**：先頭に合否と理由（理由コードの日本語の説明つき）。下に、新しいエラー（本家のログ窓風）、マップ（`map.png` と `map-baseline.png` を並べる）、C の結果（材料ごとの表）、確認していない範囲。
4. **履歴**：結果フォルダの過去の検証の一覧。選ぶと結果タブに出す。

## テスト

- 公開 CI：`Gui.Model` のビルドと単体テスト、`validation_host.py gui` の実行ディレクトリ・起動・後始末のテスト（偽の画面プログラム、ゲームのファイルなし）。
- クラウドの Linux（実ゲーム）：画面プログラムをビルドし、`xvfb-run` と lavapipe で起動する。決められた操作（例：結果フォルダを開いて結果タブを出す）の後に画面写真を撮って終了する試験用の引数を持たせ、各タブの写真を確かめる。
- ユーザーの PC：W1 と同じく手順書を送り、ユーザーが実行する。Remote Control は使わない。

## 決めたこと（試作から）

- 公開 CI では画面プログラムをビルドできない。ゲームの DLL を参照するため。代わりに画面に依存しない部分を `Gui.Model` に分けて CI で確かめ、画面そのものはクラウドの実ゲームで確かめる。
- 本家の `Page_ModsConfig` はそのまま使わない。閉じるときに設定を保存してゲームを再起動する作りのため。同じ部品で自前の窓を作る。
- Steam を初期化しないので、Workshop の MOD は自分でリンクして見せる。

## 範囲外

- 本物のゲーム画面（製造指示の画面など）の描画と、それによる C の適格化（W3）。この画面のホストは W3 の土台になる。
- 公式 `RimWorld.exe` との比較による Windows の適格化。
- イベント・クエスト・tick（C/D の今後のケース）。
- macOS、Anomaly。
