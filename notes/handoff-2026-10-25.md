# 引き継ぎ資料：RimWorld MOD をゲームなしで検証するツール

この資料は、別のAI（ChatGPTなど）がこのプロジェクトの作業を引き継ぐためのものです。2026-10-25 時点の状態を書いています。

## 1. 目的と、絶対に守る制約
- **目的**：RimWorld を起動できない環境（クラウドのLinuxコンテナなど）で、MODを「実ゲーム相当」に検証できるツールを作ること。
- **遊べる形には絶対にしない**：画面・入力・描画は作らず、テスト用途だけにとどめる。
- **ゲームのファイルは配布しない**：リポジトリ `github.com/pengin0503/RimWorld-for-mod-test` は公開設定です。ゲームのDLL、Data、逆コンパイルしたソースをコミットしないでください。Ludeon の EULA はゲームの一部をコピーして配布することを禁じています。ゲームファイルは、ユーザーがその都度実行環境に置きます。
- **Anomaly DLC は対象外**：ユーザーが所有していないため、Anomaly に依存するMODは扱いません。

## 2. 決まっていること（ユーザーと合意済み）
| 項目 | 決定内容 |
|---|---|
| 対象 | 公式 RimWorld **1.7 ベータ**（Steam の unstable ブランチ）。ベータなので頻繁に更新される |
| 最初に作る範囲 | **A**：XML の Defs・パッチ・翻訳がエラーなく読み込まれるかの検証。**B**：MODのDLLが読み込まれ、Harmony パッチが目的のメソッドに当たるかの検証 |
| 後で判断する範囲 | C：マップを生成して tick を進める検証。D：状況を組み立てて振る舞いを確かめるテスト |
| 実行場所 | クラウドのLinux（x86_64）。ユーザーは主に iPad を使うが、iPadOS は JIT が使えず Harmony が動かないため、iPad 上では実行しない |
| 方式 | **公式の `-headless` 起動＋検証用MOD**。本物の起動処理でMODを読み込ませ、同梱した検証用MODがエラーログ・Defs・Harmony パッチの当たり先を JSON に出力してから終了させる。読み込み処理だけを自前で呼ぶ「独自ホスト方式」は採用しない（実ゲームとずれるため） |
| 作り方 | 特定のAIに依存しないコマンドラインツールにする（.NET を同梱した単体実行ファイル＋手順書） |
| ゲームファイル | Linux版インストールを用意してもらう予定（現在ユーザーが準備中） |

## 3. 調べて分かった技術的事実
- 1.7 で Ludeon は Unity をやめ、自社エンジン **Waylith** に移行した（2026-10 の GamingOnLinux / PC Gamer の記事）。ゲーム本体の `Assembly-CSharp.dll` は .NET 10 向けで、UnityEngine の代わりに `UnityStubs.dll` を参照している。
- 公式に **`-headless` スイッチ**がある（`RimWorldWaylith.Program` → `Waylith.EngineApplication.RunHeadlessLoop`）。この状態では Vulkan・ウィンドウ・入力を作らない。`-QuitAfterBoot`（起動完了の180フレーム後に終了）と `-mod=` もある。
- ゲームはインストール先を `Environment.ProcessPath` から判断する。そのため `dotnet RimWorld.dll` で起動すると `/usr/lib/dotnet` をインストール先と誤認する。**起動用の実行ファイルはゲームフォルダに置く**こと。
- 必要なフォルダ：`<install>/Data`（公式MOD）、`<install>/RimWorld_Data`、`<install>/Rendering/Shaders/*.glsl`（ヘッドレスでも必須）、`<install>/Assets.zip`（無い場合は `-NoAssetPack` で起動できるが、テクスチャのエラーが出る）。
- 公式は改造版の .NET ランタイム **WaylithClr** を同梱している。設定には次のようなものがある。
  - `AssemblyNameRedirects`：UnityEngine* を UnityStubs に読み替える
  - `LaxAssemblyBinding`：アセンブリの読み込みを緩くする
  - `JitPatchableAssemblies=Assembly-CSharp`：インライン化を止め、Harmony パッチが確実に効くようにする
  - `MonoStringHashCode`：文字列のハッシュを Mono 互換にする

  標準の .NET ではこれらが再現されないので、特に B（Harmony）の結果がずれる恐れがある。このため Linux版の WaylithClr を使う方針にした。
- `0Harmony` は公式インストールに含まれない。Harmony MOD（MITライセンス、公開されている）から入手する。
- Steam のネイティブライブラリが無いと、ゲームは `Application.Quit` で終了する。ライブラリがあれば、Steam が起動していなくても警告だけで先に進む。
- 標準の音声処理はネイティブライブラリ `waylithaudio` を必要とする。試運転では、`Waylith.Audio.AudioBackend` を継承した無音のバックエンドに差し替えて回避した。
- エラーが毎フレーム出続けると、メモリが約14GBまで膨らんで強制終了される。本番のツールには、**ログの上限・タイムアウト・メモリ監視**が必須。
- DLLは必ず**同じ時点の一式**を使うこと。最初に共有された `rimworld_DLL.zip` は別々のビルドが混ざっていて起動できなかった。

## 4. ここまでの到達点
Windows版から取った .NET DLL と、Linux の標準 .NET 10 に、使い捨てのランチャーを組み合わせて試しました。ランチャーがしたことは次のとおりです。
- ヘッドレスを強制する
- 無音の音声バックエンドに差し替える
- UnityEngine* の参照を UnityStubs に読み替える
- Steam の確認処理を Harmony で飛ばす

その結果、**本物の `PlayDataLoader` が Core の XML を解析するところまで動きました**。止まった原因は `Rendering/Shaders` が無かったことです。ランチャーのソースは `notes/spike-launcher/` にありますが、使い捨ての試作なので本番には使いません。

## 5. 次にやること（この順番で）
1. ユーザーから Linux版のファイルを受け取る（必要なものは `notes/linux-files-needed.md` に一覧あり）。
2. Linux版の WaylithClr を使って `-headless -QuitAfterBoot` で起動し、Core と DLC の Defs がエラーなく読み込まれるかを確かめる。
3. 設計を節ごとにユーザーへ確認する。主な節は、ランチャー、検証用MOD、レポートの形式、実行手順の4つ。
4. 設計書をリポジトリの `docs/` に書き、ユーザーにレビューしてもらう。
5. 実装計画を作ってから実装する。
