### 判定方法の変更

ユーザーと相談し（2026-11-21）、個数の判定を次の方法に替えました。比べ直す前に方法と回数を決め、コミットしてから比べています。

- 前と同じもの：マップができたこと、設定、マップ生成の終わりまでのエラー・警告は、全回で同一であること。一部の回にしか現れない種類は、種類ごとの合計で見ること。
- 個数：判定対象の全指標をまとめて、1 つの並べ替え検定（Westfall–Young の max-T）で比べます。指標ごとの値は「|製品の平均 − 公式の平均| ÷ 全回の標準偏差」です。製品と公式のラベルを入れ替えたときの、この値の最大の分布と比べ、p < 0.05 なら差ありとします。同じ挙動なら「差あり」と出る確率は、指標どうしの相関にかかわらず 5 % 以下です（ラベルの入れ替えに対して結果の分布が変わらないことだけを前提にする）。

### 毎回違う原因

同じ種でもマップが毎回違う原因は、ゲームの `Verse.Map.NextGenSeed` でした。

```
public int NextGenSeed => HashCode.Combine(TileInfo.tile.Valid ? TileInfo.tile.GetHashCode() : uniqueID, generatedId++, Find.World.info.Seed);
```

`System.HashCode` は .NET がプロセスの起動ごとに無作為な種で初期化するので、入力が同じでも値は実行ごとに変わります。`RimWorld.BaseGen.BaseGen.Generate` は記号を 1 つ解決するたびに `Rand.Block(map.NextGenSeed)` で乱数を作り直すので、BaseGen で作る物（古代の祠＝`GenStep_ScatterShrines` の `ancientTemple` など）の中身と配置が実行ごとに変わり、その後の工程（植物、岩の欠片、動物の群れ）も違う地面の上で動くので変わります。1.7.4985 でも同じコードです。`LayoutWorker.FillAllRooms` も部屋ごとの種に `HashCode.Combine` を使います（構造物のレイアウト）。

確かめた方法（私有の調査用プローブ、コミットしていません）：

- GenStep ごとに、開始・終了時の `Rand` の状態、物の一覧と地形のハッシュを記録しました。map-genstep-throws を製品 6 回・公式 6 回動かすと、最初の 9 工程（標高、鉱脈、岩、地形、道など）は 12 回全てで同じで、最初に違いが出たのは、古代の遺跡と祠を置く 2 工程（この記録では 1 区間）で、このうち BaseGen を使うのは祠（`GenStep_ScatterShrines`）です。各工程の始めの乱数の種（工程ごとに作り直すもの）は 12 回とも同じでした。
- `Map.NextGenSeed` だけを、同じ入力をゲーム自身の `Gen.HashCombineInt` で組み合わせるものに置き換えると、map-genstep-throws と map-core のそれぞれ製品 3 回・公式 3 回、計 12 回で、地形・屋根・物の一覧（定義・位置・向き・素材・勢力・数）・ポーンが**全て同じ**になりました。GenStep が例外を出すケースと出さないケースも同じマップです（例外を出す工程は何も置かないので、そうなるはずのもの）。

ここから言えること：製品と公式は、この種が同じなら同じマップを作ります。実際の実行では、種は両方ともプロセスごとに一様な乱数なので、マップの分布も同じになるはずで、5 回目の差（p = 0.0026）は偶然の外れと考えられます。1.7.4985 の記録にあった「文字列ハッシュの無作為化」という推測は誤りでした。公式の `RimWorld.runtimeconfig.json` は `WaylithClr.MonoStringHashCode=true`（Mono 互換の決まった文字列ハッシュ）で、製品の Worker も同じ設定を使います（[マップ生成の適格化](map-qualification.md)にも追記）。

### 完全一致の比較

原因が分かったので、分布の比較をやめ、1 回ごとの完全一致で比べる方法に替えました（ユーザーに確認中、下記）。

- `mapprobe` fixture（開発用。製品の検証フローは使いません）が、製品と公式の両方で、`Map.NextGenSeed` と `LayoutWorker.FillAllRooms` の `HashCode.Combine` だけを、同じ入力とその回の番号（fixture の `Salt.txt`）をゲーム自身の `Gen.HashCombineInt` で組み合わせるものに置き換えます。他の処理には手を入れません。置き換えたことと番号は、プローブの `map seeds` の行で両側から確かめます。
- `compare_official.py --map` は、回ごとに番号を変えた `mapprobe` の写しで製品と公式を 1 回ずつ動かし、その 2 つのマップ（地形・屋根の全マス、物の一覧〈定義・位置・向き・素材・勢力・数〉、各種の数、ポーンの種類と位置）が同じであることを求めます。マップができたこと、設定、マップ生成の終わりまでのエラー・警告が全回で同一であることは前と同じです。回の数は既定 5（`qualify_build.py --map-repeat`）。番号が違えば別のマップになるので、5 回で 5 通りのマップを比べます（結果の `distinctMaps`）。
- 違う回があれば同等にせず、結果の `runsDiffering` に違う指標と行を出します。

分布の比較より厳しい判定です。1 マス・1 個の違いでも外れ、偶然には外れません（種が同じなら、製品も公式も毎回同じマップを作ることを上で確かめました）。製品の実際の検証では種を固定しないので、製品のマップは今までどおり実行ごとに変わります（結果の `map.variation`）。

### D

D は全ビルドで実験機能です。1.7.4985 で実験機能として使えるようにした根拠は、実ゲームでの受入 10 ケース（[記録](2026-10-29-bounded-tick.md)、`tests/integration/run_bounded_tick.py`）と v2 の確認（`run_bounded_tick_v2.py`）でした。公式の tick ループとの独立比較（`compare_ticks.py`）は、固定視点が生成ごとに変わる開始地点に依存するため、1.7.4985 でも一致したことがありません（[記録](2026-10-29-bounded-tick-independent-comparison.md)）。

3 回目の自動比較は、誤ってこの独立比較を実験機能の条件にしていたため、D を与えませんでした（1.7.5014 でも 3 回とも視点 x/z と描画系の診断の違いで不一致。1.7.4985 と同じ理由）。`qualify_build.py` を、1.7.4985 と同じ根拠（受入 10 ケース全部と v2）で判定し、独立比較は情報として記録するだけに直しました。4 回目の結果：

- 受入 10/10：60/600 tick でゲームの tick と fixture の Counter が 0/60/600 で一致、ベースラインの再利用、期待値違いは `failed`、未知の ID・probe なし・途中の例外は `incomplete`、時間・メモリ・ログの上限で止めたときも途中の観測を残し、子プロセスを回収。
- v2 3/3。
- 公式 tick ループとの独立比較（情報）：3 回とも不一致（`independentObservationsDiffer`、両側の `diagnosticsOrExit`）。tick 番号と Counter は一致し、違いは視点 x/z と描画系の診断で、1.7.4985 と同じ理由です。
