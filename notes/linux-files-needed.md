# 次に必要な Linux 版ファイル

対象は **RimWorld 1.7 unstable、Linux x86_64 の正規インストール一式**です。同じ更新時点のものを揃えてください。今回の Windows 版との混在は避けます。新しいビルドでも構いませんが、その場合は以後その一式を基準に再調査します。

## まず送ってほしい範囲

Linux 版インストール先から、次の 1〜3 を同時に取得してください。ファイル名は配布形式で変わる可能性があるので、例のファイルだけを選別するより、フォルダ構造を保ったままコピーする方が確実です。

| 順序 | 範囲 | 理由 |
|---|---|---|
| 1 | インストール直下のファイルすべて | 拡張子なしの公式実行ファイル、managed DLL、runtimeconfig/deps JSON、WaylithClr、ネイティブ依存関係、Steam の設定など |
| 2 | `Rendering/` 全体 | ヘッドレスでも `Rendering/Shaders/*.glsl` のソースを登録する |
| 3 | `RimWorld_Data/` 全体（存在する場合） | 起動時に使うリソース。存在しない場合は、無い旨を知らせてほしい |

`.so` の例は `libcoreclr.so`、`libclrjit.so`、`libhostfxr.so`、`libhostpolicy.so`、Steam・音声系などです。これは Linux 版の現物をまだ確認していない段階の例示で、正確なファイル名や配置の確定リストではありません。ランタイム等がサブフォルダにある場合は、そのサブフォルダも含めてください。

可能なら実行権限とシンボリックリンクを保てる `tar.gz` でまとめます。ZIP でも受け取れますが、実行権限が失われていないかをこちらで確認します。ZIP 形式の分割ファイルと、独立した複数の ZIP は別物なので、分割方法も一言添えてください。

## 起動確認には Data とアセットも必要

- `Data/Core/` 全体。
- 所有している検証対象 DLC の Data 全体。今回の対象候補は Royalty、Ideology、Biotech、Odyssey。Anomaly は対象外。
- 直下の `Assets.zip`、各公式コンテンツにあるアセットパック、またはそのビルドが実際に使用する完全なリソース一式。

Defs、Patches、Languages、About だけを抜き出した Data では、正常起動や素材参照の検証には足りません。

**追加の `Rim_data_1.zip`〜`Rim_data_3.zip` は受領・検査済みです。元の ZIP の再送は不要です。** Core と対象 DLC のデータ、DLC アセット 4 個を確認しました。今回未受領なのは Core 用アセットパックです。GLSL 225 個は `Core/Shaders/` にありますが、受領 DLL が起動時に要求する `Rendering/Shaders/` の代用になるかは未確認です。詳細と件数は [分割 Data の調査](../docs/research/2026-10-25-split-data-audit.md) にあります。

今回の Data が Linux 一式と同じ更新時点かは別途照合します。DLC の `About.xml` にある `1.7` だけでは細かなビルドの一致を証明できません。OS に依存しなさそうな XML や画像でも、ビルド間の互換性まで保証されるわけではありません。Linux の版が異なる場合は、その版の公式コンテンツへ揃えます。

## 送らなくてよいもの

- ユーザー設定・セーブの保存先（`Config/`、`Saves/`、`RimSaves/`、`Logs/` など）。
- `ShaderCache/`、`BundleCache/`。生成されたキャッシュは公式 GLSL やアセットの代用にはなりません。
- 大量の Workshop MOD。最初の試験は Core のみ、その後に所有 DLC を追加します。
- Anomaly のデータ。

`RimWorld by Ludeon Studios.zip` は今回確認した限り、この「ユーザー設定・セーブの保存先」のアーカイブでした。Windows では Steam ライブラリの `steamapps/common/RimWorld` と、AppData 側の保存先を区別する必要があります。Linux 版についても同様にインストール先を選んでください。

Linux 版を用意できない場合、今回の方針ではゲーム本体による検証は進められません。標準 .NET を使った Windows DLL の試作結果を、本番の検証結果に読み替えません。

## 受け取った後の順序

1. 非公開の入力領域で ZIP/tar の整合性、展開サイズ、パストラバーサル、リンク先、ファイルの実体を確認する。実行権限・ELF のアーキテクチャ・ランタイムの配置も確認する。
2. 各ゲーム DLL の hash、MVID、バージョン、runtimeconfig/deps と公式コンテンツのバージョン情報を記録する。互換性が不明なら起動前に止める。
3. 元のインストールを保持し、検証専用コピーを作る。Core だけを配置し、ユーザー設定・キャッシュを引き継がない。
4. プロセス外のタイムアウト・ログ容量・メモリ監視を付けたうえで、公式実行ファイルを `-headless -QuitAfterBoot` で起動する。独立した絶対パスの `-savedatafolder` を指定する。**不足ファイルを無視させるスイッチや、Steam を迂回するパッチは使わない。**
5. 終了コードだけでなく、読み込み完了、ログ、実際の Core の状態を確認する。`-QuitAfterBoot` が終了しても、それだけで検証成功とはしない。
6. 所有 DLC を追加して基準試験を行う。Steam 未起動時、音声の null 出力、ヘッドレスの完了条件はここで実測する。
7. 基準試験の結果を設計案へ反映してレビューを受け、実装計画と本実装へ進む。まず検証用 MOD 自体の有無で差が出ないことを確認する。

これらは今後の手順です。今回 3〜7 を実行したという意味ではありません。製品 CLI のコマンド名やオプションもまだ実装されていません。
