# Windows 版 W2：GUI の設計

日付：2026-10-26。状態：**ユーザーの確認待ち**（方式の選択）。前提は [Windows 版の設計](2026-10-26-windows-host-design.md) の W1（実装済み・PR #10 でマージ）。

## 目的

ユーザーが自分の Windows PC で、本家に似た画面から次の 3 つを行えるようにする。

1. 検証する MOD と構成（公式 DLC・依存 MOD・読み込み順・対象 MOD）を選ぶ。
2. 検証内容（A/B、マップ、C の材料候補）を指定して、W1 の検証を実行する。
3. 結果（合否・理由・新しいエラー・マップ・C の結果・確認していない範囲）を見る。

既存の事前検査 GUI（`tools/preflight_gui.py`、tkinter）を置き換える。検証そのものは今の `validation_host.py run` を呼ぶだけにして、判定の処理を GUI 側に作らない。AI が Linux で出す結果と、GUI で見る結果は、同じ `result.json` から作られる。

守ること：

- 遊べる状態にはしない。ゲームの画面を開いたり、コロニーを操作したりする機能は作らない。
- ゲームの素材（テクスチャ・フォント）は公開リポジトリに入れない。ユーザーの PC のゲームから、その場で私有のキャッシュに取り出して使う。
- Linux 版は AI 用のままで、人向け画面は必須にしない（同じ GUI は Linux でも起動はできるが、それは開発とテスト用）。
- 結果は Windows でも `experimental` のまま表示する。GUI が判定を書き換えることはない。

## 調べて分かったこと（2026-10-26）

- ゲームの UI 素材は `Assets.zip` の中にある（Linux 版・ユーザーの Windows 版の両方に存在）。中身は zstd 圧縮（ZIP の方式 93）で、Python 3.12/3.13 の標準ライブラリでは展開できない（3.14 からは標準で可能）。
- UI のテクスチャは DDS。調べた `Textures/UI` の 536 枚は、BC7 が 523 枚、RGBA8 が 8 枚、BC4 が 5 枚。
- ゲームに同梱の部品だけで展開できることを、Linux 版で確かめた。`ZstdSharp.Decompressor.Unwrap` で zstd を展開し、`AssetRipper.TextureDecoder.Bc.Bc7.Decompress(data, width, height, out byte[])` で BC7 を展開すると、`ButtonBG`（64×64）の画素が Pillow の展開結果と一致した（出力は BGRA の順）。.NET の `ZipArchive` は方式 93 を展開できないので、ZIP の中の位置は自分で読む。
- フォントも `Assets.zip` にある（`Arial_medium.ttf`、`Calibri_tiny.TTF`、`Pretendard-Regular.otf`）。
- 本家の窓の配色はコードの定数で決まっている。窓の背景 (21, 25, 29)、窓の枠 (97, 108, 122)、区画の背景 (42, 43, 44)、区画の枠 (135, 135, 135)、選択肢の文字 (0.8, 0.85, 1.0)。ボタンやタブは、テクスチャを 9 分割して伸ばす方式（`ButtonBG`・`TabAtlas` など）。
- ユーザーの PC のゲームフォルダには `Mods` と `RimPy_Windows` があり、Workshop の MOD は Steam ライブラリの `steamapps/workshop/content/294100` にあると見込まれる。

## 方式の比較

1. **推奨：PC の中だけで動く小さな Web 画面。** Python の標準ライブラリで `127.0.0.1` だけに待ち受けるサーバーを立て、既定のブラウザ（Edge など）で開く。画面は HTML/CSS/JS で、外部のサイトから何も読み込まない。
   - 本家の見た目に近づけやすい。9 分割のテクスチャは CSS の `border-image` でそのまま再現でき、フォントも `@font-face` で使える。
   - 画面をこのクラウドの Linux でも開いて、ブラウザで自動テスト・画面写真を撮れる。iPad のユーザーに画面の見本を送れる。
   - 欠点：別の窓ではなくブラウザのタブで開く。ローカルのサーバーを守る対策（下記）が要る。
2. tkinter（今の事前検査 GUI を拡張）。標準ライブラリだけの普通の窓になる。ただし 9 分割のテクスチャやフォントの読み込みが苦手で、本家に似せるのが難しい。画面の自動テストもしにくい。
3. ゲーム自身の描画（Waylith の Vulkan・ImGui）で画面を描く。見た目は最も本家に近いが、ゲームの描画を起動することになり、W3（実画面の描画）の調査が終わる前には危険が大きい。W3 の後で再検討する。

## 推奨方式（1）の設計

### 構成

- `tools/gui/server.py`：標準ライブラリの HTTP サーバーと JSON API。検証は `validation_host.py run` を子プロセスで起動し、その出力（進捗）を画面に流す。判定はしない。
- `tools/gui/static/`：`index.html`・`app.css`・`app.js`。ビルド工程も外部ライブラリも使わない。
- `tools/gui/library.py`：MOD の一覧（ゲームの `Mods`、Workshop、追加フォルダ）、`About.xml` の情報と依存関係、本家の `ModsConfig.xml` からの読み込み順の取り込み。今の `mod_preflight.py` の探索を使い回す。
- UI 素材の取り出し：Worker に、ゲーム同梱の部品で `Assets.zip` から必要なテクスチャ（約 100 枚）とフォントを取り出す処理を足す。出力先は私有のキャッシュ（Windows では `%LOCALAPPDATA%\rwmt\ui-cache`）。素材がなくても、上の配色だけで画面は動く。
- `Start-Windows.cmd` は新しい GUI を開くように変える。今の事前検査は、GUI の中の「事前検査」として残す（CLI もそのまま）。

### 画面

本家の画面にならって 4 つの画面を持つ。

1. **準備**：ゲームのフォルダ、スナップショットの状態（版・Adapter・`buildPlatform`）、Worker の有無。未準備なら `prepare-game` をボタンで行う。
2. **MOD 選択**（本家の MOD 管理画面風）：左に未使用、右に使用中の一覧。並べ替え、対象 MOD の印、公式 DLC の選択、`Preview.png` と説明の表示、足りない依存 MOD の警告。本家の現在の読み込み順を取り込むボタン。
3. **検証内容**：A/B の選択と言語。マップ（種・バイオーム）。C の材料候補（レシピ・材料・表示されるべきか）。Harmony の期待値など細かい指定は、要求 JSON を直接編集する欄で行う。
4. **実行と結果**（本家の読み込み画面風の進捗 → 結果）：先頭に合否と理由（理由コードの日本語の説明つき）。タブで、新しいエラー（開発者ログ風）、マップ（拡大・移動、対象と対象なしの比較）、C の結果（製造指示の画面風の表）、確認していない範囲。過去の結果の一覧も開ける。

### ローカルサーバーの守り

- `127.0.0.1` だけで待ち受ける。起動ごとに乱数のトークンを作り、ブラウザを開く URL に含める。API はトークンと `Host` ヘッダーを確かめ、合わなければ拒否する（他のサイトからの悪用を防ぐ）。
- 読めるファイルは、画面の静的ファイル、UI 素材のキャッシュ、GUI が作った結果フォルダの中だけ。任意のパスは読ませない。
- 検証の実行は一度に 1 つ。中止ボタンは W1 と同じ止め方（Job ごと停止）になる。

### テスト

- API と MOD 一覧は、標準ライブラリの `unittest` で、Linux と Windows の公開 CI で動かす（偽 Worker、ゲームのファイルなし）。
- 画面は、このクラウドの Linux でブラウザを動かして、偽の結果を表示した写真を撮って確かめる（公開 CI には入れない）。
- 実ゲームでの確認は、W1 と同じく手順書を送り、ユーザーが自分の PC で行う。

## 範囲外

- 本物のゲーム画面の描画（W3）。C の適格化。公式 `RimWorld.exe` との比較による Windows の適格化。
- イベント・クエスト・tick（C/D の今後のケース）。これらができたら結果のタブを足す。
- macOS、Anomaly。
