# 有限 tick 検証 D の具体案（未実装）

目的は、ロード後の処理を固定した短い時間だけ進め、決めた時点の状態を検査すること。
無期限実行、プレイ画面、継続セーブは提供しない。これは次段階の設計案であり、実装済み・適格化済みではない。

## 初期範囲

Linux x86_64 / ゲーム同梱 WaylithClr / 対応ビルドに限定する。生成マップと自作 fixture のみで開始する。
任意MODのイベントを自動探索せず、観測するfixtureの識別子と値を事前登録する。
検証は一時ワールドから毎回開始し、baselineとtargetを別プロセスで実行する。

## 要求案

`levels` に `D`、`tests` に `bounded-tick.v1`、`map` と次の設定を明示する。

```json
{
  "tick": {"count": 600, "observeAt": [0, 60, 600]},
  "expectations": {
    "tickObservations": [
      {"tick": 600, "id": "fixture.counter", "equals": 600}
    ]
  }
}
```

- countは整数1～60,000。最初の受入ケースは60/600 ticksに限定し、上限値は実測で再評価する。
- observeAtは重複なしの昇順整数、0～count、最大64件。最後にcountを含める。
- fixture観測IDは許可リスト方式。初版は整数値のequalsのみ、観測行は最大64件。
- tick指定のない従来要求は従来どおり動く。tickに対応しないビルドではblocked。
- limitsの実時間・メモリ・ログ制限を必ず適用し、countまで到達しなければincomplete。

## 実行と証拠

実ゲームTickManagerの単一tick処理の呼出経路と、開始時のtick番号を調査してから実装する。
ホスト側カウンターだけでtick到達を証明しない。ゲームのtick番号の実差分とfixtureの独立した状態を記録する。
tick 0の初期観測、要求した中間点、最終点の観測を順番に取得し、追加のtickを進めない。
ゲーム内のイベント処理が必要とする初期化が揃わない場合、空の代用実装で合格させない。

## 判定

到達済みの確実な観測値が期待に違えばD段階failed。観測ID不明、未到達、例外、打切りはincomplete。
新規ロード・実行エラーは従来の診断にも残す。独立適格化までは全体experimental/incompleteを維持する。
時間経過の検証は、長期プレイ、描画、Windows、他のMODや他の初期条件の保証にならない。

## 実装前の受入条件

0/60/600の観測と最終tickの一致、間違った期待値、不明ID、途中例外、時間・メモリ上限、途中停止後のプロセス回収を試す。
公式の同じ初期条件との独立比較方法を決める。乱数差が残る状態は正確な個数一致の根拠にしない。
baselineキャッシュキーにtick設定と観測仕様を含め、既存A/B/C結果をDへ流用しない。
