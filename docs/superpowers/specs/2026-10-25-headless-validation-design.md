# RimWorld MOD 読み込み検証ツール：設計案

日付：2026-10-25。状態：**レビュー用・未承認、未実装**。

実装計画を立てる立場での独立レビューを 1 回実施し、計画を左右する追加質問は残らないとの結果でした。これはユーザーの設計承認や Linux 実行確認を代替しません。

## 1. 目的、既存の合意、今回の提案

RimWorld を通常起動できないクラウドの Linux x86_64 環境で、公式 1.7 unstable と同じ読み込み処理を使って MOD を調べる。ユーザーは iPad から依頼・結果確認ができ、実行自体は Linux で行う。特定の AI を必要としない CLI と説明書を最終成果物にする。

引き継ぎ資料で合意済みなのは、公式 `-headless` と検証用 MOD の組み合わせ、A/B を先に扱うこと、Linux 版 WaylithClr の使用、ゲームファイルを配布しないこと、Anomaly を対象外にすること。これらの方針は変更しない。

**以下のランチャーの細部、上限値、JSON、終了コード、検証手順は今回の提案であり、ユーザーが承認済みの仕様ではない。** Linux 基準試験の前提がまだ揃っていないため、実装計画はその試験と本設計の確認後に作る。

### 対象と成功の意味

| 範囲 | 確認すること | ここでは証明しないこと |
|---|---|---|
| A | 公式の XML/Defs/パッチと、指定言語の読み込み、起動時の参照解決・エラー検査 | レシピやジョブがプレイ中に正しく動くこと、全画像の正確な描画、選んでいない言語 |
| B | 実際にロードされた MOD DLL と、起動完了時点の Harmony パッチ登録・期待した適用先との一致 | パッチ済みメソッドを実際に呼んだ結果、tick 後に登録されるパッチ、transpiler の意味的正しさ |
| C/D | 今回は未実装 | マップ生成、tick、シナリオ実行、セーブを使った振る舞い検証 |

画面・操作・プレイ用 API は提供しない。依頼された MOD のゲーム起動時の処理は実行されるが、ツール自身がマップ生成やセーブロードを要求しない。

### 方式の比較

| 方式 | 利点 | 問題・判断 |
|---|---|---|
| 公式 Linux 実行ファイル + 同梱 WaylithClr + 検証用 MOD | 公式ローダーとランタイムを使える | Linux の完全な一式が必要。引き継ぎで採用済み |
| 標準 .NET + Windows DLL + 起動処理の差し替え | 前の試作で Core XML の解析まで進めたとの報告 | CLR の挙動差、ネイティブ依存、差し替えの影響が残る。互換性試験の本番には採用しない |
| ゲームのロード処理を呼び出す独自ホスト | 一部だけ実行しやすい | 本来の起動順序からずれる。引き継ぎで不採用 |

## 2. ランチャー

### プロセスとランタイムを分ける

ランチャーは C#/.NET 10、linux-x64 の自己完結・単一実行ファイルを提案する。ランチャーの標準 .NET と、ゲームの WaylithClr は**別プロセス**にする。ゲーム DLL をランチャーにロードせず、標準 CLR をゲームへ注入しない。

ゲームは検証専用コピー内の公式 Linux 実行ファイルで起動する。`dotnet RimWorld.dll` に置き換えない。ゲームを起動する前に、ELF、実行権限、runtimeconfig/deps、必要なパスとランタイムの識別を検査する。設定に WaylithClr と書いてあるだけでランタイム確認済みとはしない。

### 入力と作業領域

製品の初版では、**展開済みインストールフォルダと MOD フォルダ**を入力とする。任意の ZIP/tar の安全な展開機能は製品の初版に含めない。添付受け入れ時の展開は別の準備作業とする。

元の入力は変更せず、実ファイルのコピーで検証領域を作る。まず正しさを優先し、共有キャッシュや hardlink による最適化は後で判断する。ゲームが書き換える可能性のある場所を元ファイルと共有しない。追跡対象外の run ごとの領域に以下を置く。

- 公式実行ファイル、managed/native の一式、Shaders、リソース。
- 検証対象として指定した Core/所有 DLC の Data とアセット。
- 必要な依存 MOD、対象 MOD、検証用 MOD。
- 独立した設定・保存先、ログ、検証要求、結果。

Core 基準試験では DLC を置かない。DLC 試験では指定した所有 DLC だけを置く。元のユーザープロファイル、セーブ、キャッシュ、Workshop の自動探索結果を再利用しない。配置した全 packageId と出所を manifest に記録し、重複した packageId、欠損した依存、対象外 Anomaly は起動前に拒否する。

### MOD と設定の選択

検証用保存先に新しい `ModsConfig.xml` と `Prefs.xml` を作る。実物で確認したルートは `ModsConfigData` と `PrefsData`。バージョン、`activeMods`、`knownExpansions` を明示し、公式の設定移行・新 DLC 検出の影響を基準試験で確認する。

`-mod=` を厳密な選択手段には使わない。実物では公式 DLC の追加、自動ソート、不明 MOD の警告継続があるためである。入力で求めた完全な packageId の**順序付きリスト**と `LoadedModManager.RunningModsListForReading` を突き合わせる。大小文字等の正規化規則を一つに決め、比較前後を記録する。順序違いも成功扱いにせず、入力の修正を促す。

検査モードでは `devMode=true`、`resetModsConfigOnCrash=false` とし、その実効値も報告させる。これにより公式の Def エラー検査を有効化し、失敗後の Core 等への自動回復を防ぐ。設定が効いたことを確認できなければ A の完全な合格とはしない。言語は毎回指定し、英語・日本語などは別プロセスで実行する。

### 起動と終了

常に `-headless` を指定し、描画やマップ生成に切り替わる追加引数を製品の利用者から自由には受け取らない。保存先は絶対パスの `-savedatafolder` で固定する。キャッシュと最初期ログの出力先も Linux 基準試験で確認し、run 外へ漏れる版では対応を止める。

プローブなしの最初の試験では `-QuitAfterBoot` を使う。プローブを使う製品実行では、完全なレポートの保存後に公式の終了 API を呼ぶ。公式の自動終了を併用するかは基準試験で決めるが、**レポートなしの終了は成功にしない**。Steam チェックの無効化、音声バックエンドの独自差し替え、`-NoAssetPack` による欠損無視は行わない。

### 外部からの監視（提案する初期値）

| 項目 | 値・挙動 |
|---|---|
| 実行期限 | ゲーム起動から 180 秒。準備のコピー時間とは別に記録 |
| メモリ | 子プロセス群の RSS 合計 4,096 MiB を停止の閾値にする |
| ログ | stdout/stderr/ゲームのファイルログの観測総量 32 MiB を停止の閾値にする |
| 構造化したメッセージ | 最大 2,000 件、各本文・stack trace 最大 16 KiB。省略数を報告する |
| ポーリング | 100 ms を目安にし、ストリーム読取では蓄積前に容量を制限 |
| 停止 | 対象の process group に終了要求、2 秒後も残れば強制終了。子孫も回収 |

RSS ポーリングは厳密なメモリ上限ではない。委譲された cgroup v2 が利用できる場合は hard limit を併用し、その有無を結果に記録する。利用できなければ監視方式と超過の可能性を明示する。ログのポーリングにも超過幅があり、無制限に RAM へ読み込んでから切り詰める実装にはしない。

stdout/stderr は起動直後から非同期に読む。ゲームのファイルログも同時に監視し、最終結果の判定はプロセス終了後のログ回収まで待つ。同じメッセージの複数経路での観測は件数を単純合算せず、出所と重複の扱いを記録する。意味解析できないログ形式や欠けたログは、明示的に `incomplete` とする。

## 3. 検証用 MOD

最初は自前の小さな観測用 MOD を作る。ゲーム DLL は参照としてのみ使用し、ビルド出力・配布物へ同梱しない。A の観測用 MOD 自体は Harmony に依存させない。

### 起動時の役割

MOD の生成時に runId/nonce 付きの検証要求を読み、ログを有限量で観測する。生ログを全面保持しない。最初期エラーは親プロセスの収集で補うため、MOD の購読開始以前も見えたことにはしない。

`[StaticConstructorOnStartup]` や `LongEventHandler.ExecuteWhenFinished` は後処理の順序確認に使えるが、単にコールバックへ到達しただけでは完了としない。候補は、エンジンの更新後に `PlayDataLoader.Loaded`、`LongEventHandler.AnyEventNowOrWaiting`、起動時 static constructor の完了状態を確認する方法。**正確な観測フックとタイミングは実装者が Linux 試験で選び、検証する事項**とする。

親は要求した runId/nonce と完了マーカー、実際のゲーム/ランタイム、MOD リスト、言語、設定を照合する。前回のレポートが残っていても合格に使わない。レポートは同一ディレクトリの一時ファイルへ書き、flush・close 後に rename する。後処理や終了時に出たエラーも親が確認し、途中の成功スナップショットで最終判定を確定しない。

### A の収集内容

- 選択した言語、DevMode、回復設定、ロード対象と順序。
- Def 型ごとの件数、必要な場合は期待する defName の存在。巨大な Def オブジェクト全体は JSON 化しない。
- 公式ロード中の警告・エラー・例外と、取得できた出所。根拠のない MOD への責任割り当てはしない。
- XML パッチと参照解決の診断。headless で観測できない描画・音の実動は coverage に含めない。

全 Def を逆引き・列挙できたというだけで Def の内容が正しいとは判定しない。Def 数・manifest の肥大化にも件数/バイト上限を設け、上限到達は `incomplete` にする。具体的な上限は基準試験の実測から実装者が設定し、設定値を結果に含める。

### B の収集内容

実行に使う 1.7 対応 Harmony MOD の版と hash を記録する。別版の `0Harmony` を観測 MOD から重ねてロードしない。A のみなら Harmony が無いことは B の失敗ではなく `notRequested` とする。

観測アダプターで、ロード済みアセンブリ、Harmony owner、元メソッド、prefix/postfix/transpiler/finalizer の各パッチメソッドを列挙する。元メソッドにはアセンブリ名・型名・メソッド名・引数型・generic arity を保存し、オーバーロードを区別する。必要に応じ MVID/token も版ごとの識別補助として保存する。

B を合格にするには、対象 MOD の作者または検証依頼が指定した**期待パッチ一覧**との照合が必要。期待値なしの列挙だけなら `incomplete` として、「登録されたパッチが見えた」とだけ報告する。期待値には owner、元メソッドの完全な指定、パッチ種別、パッチメソッドを含める。全体件数が 1 以上という条件では合格にしない。

Harmony の候補 API は `GetAllPatchedMethods` / `GetPatchInfo`。具体的な公開 API・型・版の対応は、実行用 Harmony を入手した時点で確認する。アダプター非対応、複数版の混在、列挙失敗を空配列による成功にはしない。パッチのコール順序や、後から変化する登録の完全な保証はこの初版の対象外。

## 4. レポートの形式と合格判定

JSON の schemaVersion、toolVersion、runId、開始/終了時刻、検証要求、入力 fingerprint、起動段階、coverage、測定値、上限、診断、最終結果を保存する。未確認の件数は `null`。未実行を 0 件として表現しない。

| 結果 | 意味 |
|---|---|
| `passed` | 依頼された全検査について完了を観測し、期待値が一致、判定対象のエラーがなく、観測欠落もない |
| `failed` | 完了した有効な検証で、対象のロードエラーや期待値不一致を確認した |
| `blocked` | 起動前提が不足、非対応のランタイム、基準試験未成立などで検証を開始できない |
| `incomplete` | 起動後の timeout/crash、プローブ不在、ログ欠落、上限到達、B の期待値不足などで結論を出せない |

各検査には上記の状態に加え `notRequested` を認める。A のみを依頼して B が `notRequested` でも、A の条件を満たせば全体は `passed`。要求されていない機能が一つも動いていない空の検証は `blocked` とする。

全体判定の順序は、起動前に止まったものは `blocked`、起動後に観測が不足したものは `incomplete`、観測が揃っていて対象の問題があれば `failed`、それ以外で全要求を満たせば `passed`。失敗を観測していても途中で落ちた場合は、全体 `incomplete` と診断の確定エラーを両方残す。

警告は保持する。既知の Steam 未起動警告等を自動で無視せず、許可する場合は版・条件・理由を明示した規則として報告する。予期しない警告が残る場合は、初版の厳格判定では `failed` とする。初回の Linux 試験で基準ログを確認する前に包括的な除外規則を作らない。

プロセスの終了コード 0、Core の存在、Harmony の全体件数だけでは合格にしない。レポートとログの観測不足がある場合は、エラーが見つからなくても `passed` にしない。

ランチャーの終了コード案は `0=passed`、`1=failed`、`2=blocked`、`3=incomplete`。ゲームの終了コードはこれとは別フィールドに保存する。ランチャー自体の内部エラーも診断に残し、起動前なら blocked、起動後なら incomplete として JSON を可能な限り生成する。

## 5. 実行手順と検証の進め方

最初に [ファイルの受け入れ](../../../notes/linux-files-needed.md) を済ませる。製品を実装する前の基準試験では、Core、次に所有 DLC を、プローブなしの公式 headless で実行する。実際にどこまで完了を証明できたかをログ付きで非公開に記録する。ファイルが揃わなければ、この工程は blocked のままにする。

その結果と本設計のレビューを経て実装計画を作る。実装中は次を満たす。

1. ランチャーの process 監視・終了・ログ上限・stale report 拒否は、ゲームファイルを使わない自前の子プロセス fixture で検証する。
2. 正常な小 MOD、壊れた XML、失敗するパッチ、解決不能なクロス参照、起動時例外、不正な選択言語データ、期待 Harmony パッチ欠落を、**自前の最小 fixture**で区別できることを確認する。
3. 検証用 MOD を加える前後で、公式コンテンツの Def 件数と起動ログに予期しない差がないことを確認する。
4. Core の英語、Core の日本語、所有 DLC の組み合わせ、対象 MOD と依存 MOD の順に実行する。対象のない言語・DLC は実行済みに数えない。
5. 正常系だけでなく、MOD の自動回復、プローブ未ロード、レポート途中書き、1000 件超のログ、timeout、メモリ超過、子プロセス残留、ゲーム更新を試す。

公開 CI はゲーム不要の単体・fixture 検査とビルドに限る。実ゲーム検証はユーザーが管理する非公開領域で実行し、ゲームファイル・ユーザーログを Actions artifact や Release にアップロードしない。CI が通っても実ゲーム検証済みとは表現しない。

### 配布物

最終的にはランチャー、検証用 MOD、自前の fixture、手順書を配布する。ゲーム本体と公式コンテンツは含めない。自己完結ランチャーの標準 .NET の再配布条件と third-party notices は別に確認する。Harmony を同梱する場合はその実物のライセンスと版を確認するが、初版はユーザー提供の対応 MOD を入力として使う案とする。

## 6. 実装者が決める項目と、レビューで確認する項目

実装者が決めるもの：クラス分割、CLI の最終的なオプション名、アーカイブを扱わない初版の内部構成、選んだ Harmony 版に対する観測アダプター、実測に基づく manifest/Def/パッチ一覧の上限、Linux 上で確認した正確な完了フック。

レビューで確認するもの：ランチャーと観測 MOD の責務、言語ごとの別実行、起動時登録までに限定した B の意味、期待パッチ一覧がない場合に B を合格にしないこと、初期監視値、警告を厳格に扱う方針。

未確認の環境事項：Linux 版の正確なネイティブ配置、glibc 等の互換性、Steam 未起動時の経路、音声 null 出力の動作、公式 headless の基準ログ、書込み先の隔離、完了フックと自動終了の順序。これらはユーザーに推測で答えてもらう事項ではなく、Linux 一式を受け取って測定する事項である。
