# Linux 検証の設計提案（2026-10-27）

この文書は提案であり、実装・実ゲーム確認・適格化を意味しない。各ケースは対象ゲームビルド、runtime、adapter と観測範囲に限定する。

## C: 材料候補の非描画での根拠

Linux では描画しない。固定したレシピ・材料・カテゴリ・フィルターを持つ自作 fixture で、Controller が観測した候補と許可状態を、ケースごとに独立して記述した期待一覧と比較する。カテゴリの親子、特殊フィルター、禁止・許可、複数材料と、ユーザーの小麦粉 MOD で確認済みの再現版・修正版を含める。実ゲームの同じビルドとロード順で正例・負例をまとめて実行し、ゲーム API の判定と結果形式を確認する。これは非描画の表示ロジックの根拠であり、描画結果の一致は主張しない。独立性や適格化基準を満たすまで `experimental` / `incomplete` を維持する。

## C: イベント・クエストの最初のケース（承認待ち）

提案対象は自作 fixture の選択肢付きイベント。固定 seed と初期マップで、対象イベントを限定的に発生させ、指定した選択肢を一度だけ選ぶ。選択後の報酬、状態変化、エラーの有無を期待値と比較し、イベント ID、発生、選択肢 ID、選択後の観測、理由を出力する。発生不能、選択肢未出現、観測不足は `incomplete`、期待が確実に外れた場合は `failed` とする。fixture は特定の実 MOD の全挙動を証明しない。

## D: 有限 tick（方式了承済み、数値は提案）

固定 seed と明示した初期条件で、要求された tick 数まで進め、指定 tick で観測する。上限は当初 60,000 ticks、実時間・メモリ制限も既存 limits を適用する案。観測対象は自作 fixture の定義済み状態（たとえば特定 ID の個数と状態値）に限定し、期待値には tick、観測 ID、比較演算子と値を明示する。未到達・タイムアウト・観測不能は `incomplete`、完了した観測が期待に違うときは `failed`。無期限実行やプレイ可能な環境は作らない。tick 上限の数値と観測スキーマは実装前にさらに検討する。
