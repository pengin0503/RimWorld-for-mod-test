# AI と Windows 利用者向けの共通検査

ユーザーの新しい要求は、PC を使えない時に Linux 上の AI へ検証を任せる用途と、Windows の PC で通常起動前に自分で検査する用途の両立。これを今後の対象とし、Linux 専用という従来の制約を更新する。

## 方式と今回の範囲

1. 共通の検査処理を CLI とデスクトップ画面から使う方式を採用する。JSON は AI・自動化向け、画面は人がフォルダ選択・結果確認・通常起動するための入口とする。この入口の選定は実装上の判断。
2. OS 別に検査処理を作る案は結果が分かれるため採用しない。Windows のために WSL や Linux を必須にする案も用途に合わない。

今回は、インストール先と保存先、MOD 検索先を記録するプロフィール、現在の有効 MOD 構成に対する事前検査、Windows 用画面、検査後の明示的な通常起動を実装する。Python 3.12+ と標準ライブラリを共通基盤にする。Windows 配布 EXE と公式 headless＋観測 MOD の実ロード検証は次段階。ゲーム本体のファイルは配布しない。

## 検査と判定

保存先の `Config/ModsConfig.xml` を読み、Core・有効 MOD の存在、packageId の重複、対応ゲームバージョン、依存・競合・強制ロード順、XML の構文を調べる。設定を並べ替えたり修正したりはしない。ゲーム本来のパッチ適用・参照解決・翻訳注入・Harmony・プレイは実行しない。

検査するロードフォルダはルート・Common・指定バージョンを基本とし、LoadFolders.xml は明示的に対応した形式のみ扱う。条件やバージョン選択を判断できない場合は `incomplete` として画面にも表示し、起動許可用の完全な事前検査結果にしない。翻訳 TAR や実行時の言語注入は今回の範囲外。DLL はロードせず識別用にハッシュする。

結果は `recordType=modPreflight`、`auditStatus`、`gameVerification=notRun`、検査範囲、経過時間、入力 fingerprint を持つ。事前検査に通っても実ゲームを検証済みとは表現しない。「通常起動より高速」は未計測のため保証せず、重い画像・音声の読み込みを省いた経過時間を表示する。

## 通常起動

画面の明示ボタン、または CLI の `play --acknowledge-static-only` のみで起動する。プロフィールから選ぶ公式実行ファイルは Windows の `RimWorld.exe`、Linux の `RimWorld`。実行時に `-savedatafolder` を指定し、検査対象と通常起動の保存先を揃える。shell は使わない。

起動前に再検査し、プロフィール・ModsConfig・索引 About・検査した XML/DLL・実行ファイルが変わっていたら以前の結果による起動を拒否する。未検査リソースの不変性や実プレイの安全を保証する仕組みではない。検査中に変化するファイルは検査不能として扱う。全ゲームデータやユーザーのセーブはコピー・変更しない。

## 二つの利用経路

- AI：プロフィールを用意し、`check --profile ... --output ...` を実行。JSON の診断を使ってユーザーの依頼範囲で MOD を修正し、再検査する。Linux 正規インストールを与えれば同じ事前検査を使える。Windows DLL を Linux 用として実行しない。
- Windows：起動スクリプトから画面を開き、ゲーム・保存先・追加 MOD 検索先を指定して検査する。検査範囲と結果を確認した後に通常起動する。修正・有効 MOD の変更はユーザーまたは別の作業が行う。

## 検証

合成のゲーム・MOD フォルダを使い、両 OS の CI で同じ入力・結果・起動ガードを検査する。実ゲームは CI に送らず、ゲームがない環境では通常起動コマンドの構築と拒否条件まで検査する。GUI の実操作、通常起動、速度差、公式 headless の OS 別基準試験は未実測として残す。
