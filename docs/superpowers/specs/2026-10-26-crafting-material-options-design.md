# C の最初のケース：クラフト材料の表示候補と許可状態

状態：レビュー用の設計案。製品実装はまだ開始していない。

## 目的とユーザーが決めた範囲

以前の `pengin0503/rimworld-VCE-Flour-Patch` で、クラフト画面に必要な材料が出ない問題があった。この特定 MOD だけの修正ではなく、ほかの MOD でも同種の欠落を検出できる有限な検証ケースを C に追加する。

- Linux 版は画面を描画しない。画面で使われる実ゲームの表示候補・許可状態の処理を呼んで検査する。
- Windows 版で実画面を描画する。画像、文字の見切れ、配置、クリック等は Windows 側の別作業として扱う。
- イベント/クエストは、発生することと選択肢を選んだ後の動作が意図どおりであることが必要。ただし最初の有限ケースは材料一覧。具体的なイベント/クエスト・初期状態・期待結果は別ケースとして後から定義する。

## 検討した方法

1. Def 内の材料名・許可だけを検査：軽いが、ゲームの UI フィルターで材料が隠れる問題を取り逃がすため採用しない。
2. 実ゲームの材料一覧の判定を呼ぶ：Linux の選択した方式。ロード済みのレシピと新規製造指示を使い、材料候補・許可・表示判定を観測する。
3. 実画面を描画・比較：ユーザー指定により Windows の将来作業に限定。Linux の結果から代用・保証しない。

## 根拠となる既存処理

私有の対応 DLL で `RimWorld.Dialog_BillConfig.DoIngredientConfigPane`、`Verse.ThingFilterUI.DoThingFilterConfigWindow`、`Verse.Listing_TreeThingFilter` の表示判定経路を調べた。`Listing_TreeThingFilter.Visible(ThingDef)` は親フィルターの許可だけでなく、特殊フィルターによる常時不許可や強制非表示等も参照する。材料の Def が存在し、通常フィルターで許可されることだけでは表示候補の証明にならない。

小麦粉 MOD の既存ソースの `tests/GameRuntime/Program.cs` にもこの表示判定の回帰ケースがある。ただしそのテストは合成 Def と stub を使うため、その成功を本ホストの実ロード済み状態での C 成功とは扱わない。逆コンパイル本文・ゲーム資材は公開しない。

## 最初に実装するケース

固定したケース ID `bill-ingredient-options.v1` を設ける。任意の型名・メソッド名を要求から呼べる仕組みにはしない。

- 対象はロード済みの RecipeDef と ThingDef、およびそのレシピから実ゲームが生成する新規の製造指示。
- 表示候補の検査対象は製造指示の材料フィルター一覧。材料一覧の pane 自体が表示されるか、カテゴリツリーに到達できるか、対象材料の実表示判定と現在の許可状態を確認する。
- 各材料について `visible` と `allowed` の期待値を明示する。`visible` は pane が対象になり、材料のカテゴリ経路がその一覧の対象ツリーに到達し、実ゲームの材料単位の表示判定を通ることの AND とする。pane eligibility・カテゴリの構造的到達性と走査時の非表示・材料単位の判定を別々に記録する。
- 最初のケースは編集可能な材料 pane と解決可能なカテゴリツリーを前提とし、これらの構築/解決失敗を単なる `visible:false` で代用しない。非表示を期待するケースでも、誤ったレシピやカテゴリ欠落で偶然 false になっただけなら合格にしない。レシピ/材料がロード後に未定義、カテゴリ欠落、特殊フィルターによる非表示、全材料固定による pane 非表示を別の観測・理由として扱う。
- 材料名がデータにあるだけで合格にしない。期待していない材料を全部許可したり、検査のために実 Def やレシピを書き換えたりしない。
- 検査のための新規 Bill は run の中だけで生成して破棄する。既存セーブ・プレイヤー設定は読まない。既存セーブの Bill 移行はこの最初のケースの対象外。
- 画面上のスクロール位置、カテゴリの開閉、検索文字、ピクセル、ラベルの見切れは Linux の検査範囲外。まず検索なし・全カテゴリを対象にした表示候補を観測する。描画コールバックの内部だけで項目を消す MOD は、この非描画ケースでは取り逃がし得る。実画面の表示保証とは呼ばず、その差は Windows の描画検証で扱う。

## 要求・結果の境界（提案）

既存の `tests` を固定ケース ID の一覧として利用し、型付きの材料期待値を `expectations.billIngredients` に追加する。各項目は `recipe`、`thing`、`visible`、`allowed` を持つ。未知フィールド・未知ケース・空の検査を拒否する。A の観測を C の代わりにせず、既存の A/B 要求は従来どおり受け付ける。具体的なスキーマ検証・上限値は承認後の実装計画で固定する。

Worker は実際に呼んだケース ID、レシピ、材料、表示候補、許可、非表示理由を構造化して出す。Controller は観測完了と期待値を照合する。C の期待値は対象入りの実行で検査し、対象を外すとレシピが消えるベースラインに同じ期待値を強制しない。ベースラインは従来のロード診断比較を維持する。

既存の timeout・メモリ監視・ログ上限・有限終了を共用する。必要 API の不足や未対応要求は `blocked`、実行後の観測欠落・例外・上限・未適格は `incomplete`。全体完了・対応範囲の適格性が確認されたうえで期待と異なれば `failed`、一致すれば `passed`。新しい C を既存 A/B の適格化で自動的に `qualified` にしない。ケース単位で正例・故障例・参照動作の証拠を揃えるまで experimental/incomplete とする。

## 受入条件

- 実 Def ロード後の新規 Bill について、通常許可と UI 特殊フィルターが食い違って材料が非表示になる故障を検出する。
- 正常な材料表示、非表示を期待する材料、表示対象外のレシピを区別できる。
- 無関係なレシピや材料の制約を変えない。Bill/Def を検査のために書き換えて期待値に合わせない。
- 未知のテスト ID、空の期待値、材料/レシピ欠損、API 不足、途中例外、時間超過に対して偽の成功を返さない。
- 公開 CI は自作 fixture のみ。私有ゲーム・MOD・索引・生ログを公開しない。
- 対象 MOD を取得する前に正規索引と About を照合する。小麦粉 MOD は索引の名前検索では見つかっていないため、ソース側 About の照合と、ユーザー作成 MOD のソースビルド入力の扱いを明示してから実資材検証へ進む。正規ゲーム・Workshop 依存は引き続き R2 から必要分だけ取得する。

## 今回作らないもの

Linux の描画、Windows の実装、保存済みゲームの移行、イベント/クエストの汎用実行、D の tick、任意のゲームメソッドを呼ぶ RPC、無期限プレイ。これらを将来ケースとして残し、材料一覧の合格から保証しない。

## 設計レビュー

独立した builder check を実施。`visible` の構成要素を分離し、false が文脈の不正を隠さないこと、描画コールバック内部だけの不具合は対象外であることを明記した。残るスキーマの具体的上限値・適格化証拠・自作 MOD のソースビルド入力の扱いは、この設計の承認後に実装計画で固定する。
