# Dual-use preflight implementation plan

> Execute inline with superpowers:executing-plans and test-driven-development.

**Goal:** 同じ事前検査を AI の CLI と Windows の画面から使い、検査後の明示的な通常起動へ繋げる。
**Architecture:** Python 標準ライブラリの backend と CLI、薄い Tkinter 画面。
**Tech Stack:** Python 3.12+、unittest、Tkinter、既存 CI。
**Spec:** [二つの用途](../specs/2026-10-25-dual-use-design.md)。

## Global constraints

- ゲームファイル・設定・セーブを書き換えず、ゲーム DLL をロードしない。
- 事前検査は `gameVerification=notRun`。公式 headless は別工程。
- Windows/Linux とも同じ core を使う。通常起動は明示操作のみ。

## Review focus

- inactive MOD と active MOD、Steam の別識別子、バージョン別フォルダの取り違え。
- 設定・ファイルの変更後に古い合格結果で起動できないこと。
- ファイル・フォルダ欠損、シンボリックリンク、DOCTYPE、大きすぎる入力。
- 保存先と起動対象の一致、shell を使わないこと。
- 部分検査・未検査をゲームの合格として表示しないこと。

- [x] 最小実装後に全テストを通す。

### Task 2: CLI と通常起動ガード

- [x] 古い fingerprint、不完全な結果、保存先の指定、JSON 入出力をテスト。

## Ledger

Ruling: 対象を Windows/Linux の二用途へ広げるユーザー指示に基づき、共通の事前検査・明示起動を実装する。公式ロード検証と速度優位は未実測として表示する。事前検査を完全な互換性保証と誤解することが主要なリスク。

Tasks 1–2: RED を確認後、プロフィール・有効 MOD・XML・ロードフォルダ・CLI・通常起動ガードを実装。既存 31 件と合わせて 52 件を通過。

Task 3: Windows 画面の生成テストと判定表示を追加。独立レビューの読出しエラー・リンク経由の出力上書きを RED→GREEN で修正。最終 59 件、Linux でのネイティブ Windows 画面生成 1 件は skip。元ゲームを起動したことにはしない。

Ruling: 保存先の引数を実 DLL で照合し、`-savedatafolder=PATH` の 1 トークンに変更した。パス内の `=` 等を扱えない受領版では明示的に拒否する。代償はそのような保存先で通常起動の入口を使えないこと。

Ruling: 初回の文書どおりの CLI 実行に必要な出力親ディレクトリの作成は使用開始を妨げる問題として対応し、入力の保護判定後に作成する。テストで保護対象を書き換えないことを確認した。

Review exclusions: 実ゲームの起動・実ロードの互換性・速度優位・Windows の手動操作は未実測として扱う。ゲーム固有の意味解析は静的検査の対象外。GUI は共通 backend と直接接続するが、Windows の全手操作が検証済みとはしない。保留した本変更の小項目はなし。

CI 初回：Ubuntu 3.12/3.13 は成功。Windows はネイティブ画面生成も通過したが、一時フォルダの 8.3 短縮名と CLI が解決した正式名の違いで 2 テストが失敗。fixture のルートを resolve し、同じディレクトリを指す前提を両 OS で揃えた。製品の判定・引数処理は変更せず再実行する。
