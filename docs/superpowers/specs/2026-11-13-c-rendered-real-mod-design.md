# C材料：小麦粉MODを描画ありの公式参照と比べる設計

2026-11-13。**実施結果は[小麦粉MODの比較記録](../../research/2026-11-13-c-rendered-flour-mod.md)。** 前提は[描画ありの公式processの研究](../../research/2026-11-13-c-rendered-dialog.md)と、同日のユーザー許可（C材料の参照に限り、描画ありの公式起動を開発用比較に使ってよい。条件はAGENTS.md）。開発用の比較であり、C資格・cache・製品の判定式は変えない。

## 目的

ユーザー自作の小麦粉MOD（[rimworld-VCE-Flour-Patch](https://github.com/pengin0503/rimworld-VCE-Flour-Patch)）の不具合版と修正版のそれぞれで、次の2つを同じ構成・同じビルドで並べる。

- 製品の非描画C（`bill-ingredient-options.v1`）の答え
- 公式の実ダイアログが列挙した行

2026-10-26の[実MOD記録](../../research/2026-10-26-flour-mod-c-run.md)では、比べる相手が過去の人の報告しかなかった。今回は同じ条件で描画した実画面と比べる。

## 確認した事実（設計の根拠）

静的に読んだ事実。私有の逆コンパイル、R2のVCE Defs、Core Defs、MODリポジトリで確認した。

1. **VCEの焼き料理7レシピ**（`VCE_CookBakeSimple`…`VCE_CookBakeGourmet`）の固定フィルターは `FoodRaw` 分類と `VCE_Flour` で、特殊フィルター `AllowPlantFood` を禁止している。Gourmetだけは `VCE_Condiments` も含む。`VCE_Flour` の分類は `PlantMatter`。VCEのR2版は1.6フォルダだけを持つが、`loadFolders.xml` が1.7でも `/` と `1.6` を読ませる。
2. **小麦粉MODの版の違い**
   - 不具合版 `28cb8e5`：米粉・コーンミールを `PlantMatter` に置き、レシピの `thingDefs` へ追加する。
   - v0.1.0 `54767b2` 以降：新しい分類 `PFA_GrainFlour`（親は `PlantMatter`）に3種の粉を移す。さらに起動時、対象レシピの固定フィルターで `SetAllow(AllowPlantFood, true)` を呼ぶ。
   - 現在のmain（`20d4ae9`、v0.3.0）も同じ構成。
   - 3種の粉は `RoughPlantBase` 由来で `foodType=Plant` を持つ。Coreの `AllowPlantFood` は干し草と同等の品質の食料に当たる特殊フィルターで、`RawCorn`（`VegetableOrFruit`）には当たらない。
3. **表示ルート**：材料欄は親フィルター（レシピの固定フィルター）の `DisplayRootCategory` から始まる。これは「許可された物をすべて含む、最も深い分類」である。焼き料理の許可物は `Foods>FoodRaw` 側と `ResourcesRaw>PlantMatter` 側にまたがるので、表示ルートは全体のRootになる。
4. **既定の開閉状態**：分類の木で最初から開いているのは、全体Root直下の最初の子（Coreでは `Foods`）だけ。製造指示ダイアログの開閉マスクは4。分類の子は、その分類が開いているとき（または検索中に一致するとき）だけ辿られる。
5. **3と4の結論**：既定の状態では、どの版でも粉の行（`ResourcesRaw>PlantMatter`、修正版ではさらに `>PFA_GrainFlour`）は辿られない。`FoodRaw` も閉じているので、トウモロコシ等の行も辿られない。**展開しないままの観測では、不具合版と修正版を区別できない。**
6. **ユーザーの展開操作**：開閉ボタンを押したときにゲームが行う処理は `node.SetOpen(openMask, !開いているか)` だけ（`Listing_Tree.OpenCloseWidget`）。
7. **見えない分類**：見えない分類（`Visible(category)` がfalse）は、開閉状態に関係なく辿られない。不具合版で粉が `categoryNotVisible` になる場合、展開しても行は出ない。

## 決定

### 展開は、ゲームの開閉処理をそのまま呼ぶ

観測fixtureは、各ダイアログを開いた後、まず既定の状態のまま数回描画させ、そのときの列挙を「既定状態」として記録する。続いて、比較対象の各物について、その物が属するすべての分類の祖先を表示ルートまで辿る。そのうえで、各ノードに対してゲーム自身の `TreeNode.SetOpen(4, true)` を呼び、再び描画させた列挙を「展開後」として記録する。

これは、利用者が開閉ボタンでその分類を開くのと同じ状態変化である。

- 入力イベントは作らない。
- `Visible` などの判定、検索、隠し物の扱いは変えない。
- 見えない分類は、ゲームのコードが辿らないまま残る。

開いたノードとその前の状態は記録する。ノードの開閉状態はプロセス内の静的状態なので、ダイアログを閉じた後に元へ戻す。1回のprocessで複数のダイアログを開くため、戻さないと次のダイアログの「既定状態」が汚れる。

比較の判定には「展開後」を使う。「既定状態」は事実4・5の実測として記録するだけで、一致・不一致の判定には使わない。

却下した案：

- 検索欄に粉の名前を入れる案。一致判定が名前・翻訳に依存し、別の行も一致しうる。
- 全ノードを開く案。比較に要らない行まで辿り、時間と記録量が増える。
- 展開しない案。事実5のとおり区別できない。

### 比較する行

版ごとに、7レシピ×次の物を比べる。

| 物 | 目的 | 予想（不具合版 / 修正版） |
|---|---|---|
| `VCE_Flour`、`PFA_RiceFlour`、`PFA_Cornmeal` | 不具合の対象 | 表示されない / 表示される |
| `RawCorn` | 植物の食料だが `AllowPlantFood` に当たらない対照 | 表示 / 表示 |
| `Hay` | 既定で開いている `Foods` 直下にあるが、固定フィルターで許可されない対照 | 非表示 / 非表示 |

予想は製品リクエストの期待値として書く。ただし比較は**製品の実際の答えと公式の列挙**で行い、期待値との差は別に記録する。不具合版では製品が期待値と食い違う（`billIngredientMismatch`）ことが正しい結果なので、ゲートはこの理由と、それによるC段階の `failed` を許す。その他の理由と、実行の未完了は許さない。

### 構成

- Linux、1.7.4985 rev1269、Coreのみ、English。DLCなし。
- 依存MODは索引で確認したIDのとおり：Harmony（2009463077、`brrainz.harmony`）、Vanilla Expanded Framework（2023507013）、Vanilla Cooking Expanded（2134308519）。R2から既存の `fetch-mods` で必要なファイルだけ取得する。
- 小麦粉MODは索引・R2にないユーザー自作MODなので、10-26と同じく `--local-target` で使う。
  - 対象版：不具合版 `28cb8e5`、v0.1.0 `54767b2`、現在のmain。
  - 各版をMODリポジトリのcsprojで `RimWorldVersion=1.7` としてビルドし、配布と同じ構成に並べる。
- 観測fixtureのHarmony依存は、実行時に生成するAbout.xmlで決める。実MODの構成では `brrainz.harmony` を依存先にし、自作の `harmonylib` は入れない。fixtureの構成では従来どおり `harmonylib` を使う。
- 製品の実行・公式の対照・公式の観測は、同じMods・ModsConfig・Prefsで行う（既存スクリプトと同じ）。観測fixtureは製品側では動かない設定にする。

### スクリプトの一般化

`probe_c_rendered.py` の固定値（recipe・物・行）を、比較仕様のJSONに置き換える。既定値は現在のfixture仕様とし、現在の試験と結果を保つ。比較仕様は製品リクエストの `mods` と `expectations.billIngredients` から作る。次の点は変えない。

- 公式の「表示」は、RepaintとLayoutの両方で列挙されたことを指す。
- 診断は対照と完全一致を求める。実MODが出す警告も、対照と同じなら許す。
- `qualified` は常にfalse。

### 記録と公開

公開の要約に含めるのは、行ごとの真偽、ゲート、分類名・defNameだけ。生ログ・スクリーンショットは私有領域に置く。展開後のダイアログのスクリーンショットは、ユーザーが見られるようプロジェクトの共有フォルダにも置く（公開リポジトリには入れない）。

## 成功と失敗の扱い

- 各版で `agreement: true` なら、その版の行について製品と実画面が一致した記録になる。版をまたいで、不具合版は粉が出ず、修正版は出ることを両側で観測できれば、10-26の結論を実画面で裏づけたことになる。
- 不一致が出た場合は、その行を事実として記録し、製品の判定式は変えずに原因を調べる。どちらが正しいかは、ゲームのコードと実画面から判断する。
- 展開後も粉の分類が辿られない、例外が出る、診断が対照と違う、といった場合は「未観測」として止め、一致とは呼ばない。

## 範囲外

- C資格・cache・製品の判定式の変更。資格には別途、独立process 3回・期待値の変異・対象の不在などの条件が必要。
- DLC有効時。fresh GameにWorldがないため、Ideology有効時は `Find.IdeoManager` で例外になると静的に読める。別設計とする。
- 既存セーブのBill、製粉レシピ、実際の調理、日本語表示。
